## 1. The one failure behind most of today

The orchestrator was authoring text under its subagents' names. Every case
below is the same defect wearing a different hat.

| the agent said | the itinerary said |
| --- | --- |
| `Not connected -- the Budget agent did not run` | `Flights: $1,076 ... approximately $385 per night for lodging` |
| `Note: I interpreted "Italy" as Germany` + German data | Germany's norms relabelled as Italy's, note deleted, plus `Haggling: Not expected in Italy` |
| `Status: INCOMPLETE BUT PROMISING` | `Status: FEASIBLE BUT TIGHT` |

The last one matters most for anyone tempted to fix this with a rule: the floor
**already** said "No agent in this system prices lodging" in the same document,
a few lines under `$385 per night`. A correct notice at the bottom does not
undo a confident claim at the top. Guards that argue with output after the fact
lose.

### What changed

- **`_itinerary`** — the model writes a summary; each agent section is that
  agent's reply, verbatim. A crashed agent's section is now its crash.
- **`_bounded`** — no lodging price survives in the summary. Same `LODGING`
  pattern `_NOT_A_PRICE` already used inbound, now applied outbound. Sentence
  granularity, no exemptions: an earlier version spared lines reading like an
  allowance and the next live run walked an invented `$350-600 for
  guesthouses` straight through on the word "leaving".
- **`_HEADING` split** — rule 5 asks the model not to write sections. It wrote
  them anyway (`=== destination ===` … `=== money_customs ===`), so the summary
  is truncated at its first heading.
- **`_stated_caveats`** — `Note:` / `Assumption:` / `Adjusted:` lines an agent
  stated about its own answer are reattached if the summary dropped them.
- **`request or task`** — Budget's brief carries the traveller's words. It was
  carrying the model's rewrite, which relayed three agents' figures as
  unverified prose above the ledger and told Budget to "Determine if this fits
  the budget", contradicting rules 3 and 5 in the same prompt.
- **verbatim request to every slot** — the parser has no field for "honeymoon".
  With it, Destination returned "for a romantic 6-night honeymoon stay",
  Restaurants "for a romantic dinner", Activities "activities for your
  honeymoon".

Tests: `test_verbatim_sections.py` (29), `test_budget_brief_request.py` (6),
`test_stated_caveats.py` (3). Whole suite green except `test_agent.py`, which
fails on a missing `langchain_cerebras` and did so before today.

## 2. Emily's `money_tools.py` — take the data, the fix is two lines not one

**Take it.** 17 → 22 countries (Aruba, Barbados, Maldives, Seychelles,
Vietnam), consistent across all four dicts, no orphan keys, all four services
per entry. Measured: Aruba goes from a semantic miss to an exact hit, which
retires the `"Aruba" resolves to FIJI at 0.286` note in
`orchestrator_config.py:179`. She changed **no logic** — 15 hunks, all data plus
`match_score`/`adjusted` key padding.

**The fix `money_customs_coverage_check.py` prints is necessary but not
sufficient, and that check is misleading.** It asserts only on `found`. Applying
the one-liner takes it 5/11 → 11/11 while the live agent still answers an Italy
question with Germany's data, because `**facts` is still spread into the same
dict. A boolean does not outrank a paragraph of plausible content beside it.

Both halves, together:

```python
# search_money_customs, replacing the low-confidence result block
if match_score < CONFIDENCE_THRESHOLD:
    return {
        "country": country.strip(),          # what was asked, not what matched
        "found": False,
        "match_score": match_score,
        "adjusted": None,
        "error": (f"No money-customs data held for '{country.strip()}'. Closest "
                  f"entry is {_display_name(best_id)} (similarity {match_score}), "
                  f"too weak to answer with."),
    }
```

And the same early return in `get_comparative_context` when
`destination_customs["found"]` is false — otherwise the **home** country stays
populated and the model builds "Tipping is expected in Italy, unlike in the
USA", copying the USA `haggling_note` across verbatim as Italy's. Fixing the
first without the second made output *worse* in a measured run.

**Do not apply either before a demo.** The orchestrator chooses what string to
send, and correct answers score below the 0.55 threshold:

```
Honolulu, Hawaii, USA -> Hawaii  0.453   Cancun, Mexico -> Mexico  0.471
Hawaii, USA           -> Hawaii  0.532   USA / Mexico   -> exact
```

With the fix, a run where the model sends the longer form blanks a correct
answer. The threshold is mistuned and needs its own pass.

## 4. Budget's arithmetic is unguarded, and rule 3's premise is wrong

`orchestrator_costs` verifies every figure **entering** Budget appears verbatim
in its source. Nothing checks what Budget computes from them. Observed on
identical inputs, hours apart:

```
run A:  $154/person x 2 = $308      (correct)
run B:  "Outbound $154 x2 = $308, Return $166 x2 = $332" -> $640
```

Those are three round-trip options, all `arrives CUN`. Run B read two of them as
legs. The ledger does not label round-trip and still contains a duplicate
`"Cheapest option is AM"` entry at the same price.

Budget also invents meal counts — `~$28/person/meal x 15 meals x 2 = $840` — and
puts them in the costed subtotal. Rule 6 already has the pattern for figures
mentioned but excluded from totals; rule 1 bans estimates outright, so Budget
smuggles them in instead. Worth allowing them explicitly and keeping them out of
the total.

**Rule 3 says "No agent in this system provides accommodation costs". That is
false.** `budget_agent/data/city_cost_docs.py` holds per-night lodging for its
15 cities (`Budget hotels and hostels ... $60-100 per night`, `guesthouses run
$15-30 per night`). Budget has been reading its own corpus and being told not
to. The ban was written against agents with no lodging data — `_NOT_A_PRICE`
records Activities leaking `$300/night` derived from the traveller's own budget
— and it caught the one agent that has it. Lifting it needs Budget's coverage
check first, or one city's rates ship under another city's name.

## 5. Operational

- **OpenRouter ran to $0.14** mid-session and refused requests; five of six
  slots route through it. Reservation is against `max_tokens`, so
  `ORCHESTRATOR_MAX_TOKENS=8000` on Sonnet holds ~$0.12 per orchestrator call.
  Check the balance before demoing.
- **Money & Customs latency: 51–383s** across today's runs, median ~220s. Inside
  the 27–358s already documented, but plan for a five-minute gap. It constructs
  `ChatCohere` directly and cannot be moved.
- **Budget crashed 5 times in ~18 runs**, `KeyError` on the chroma path and
  `Could not connect to tenant default_tenant`. Clustered in rapid repeated
  runs; five consecutive full-live runs afterwards were clean, so treat 1-in-4
  as an upper bound. Its section now shows only the crash.
- **Corpus write-back fires on any uncached city.** Oranjestad, Bridgetown,
  Nassau and Montego Bay each wrote `destinations.json`,
  `destination_profiles.json` and an activities doc during testing; all
  restored. `git status` after every run with a new city.
- **Frankfurter carries 30 currencies; 12 of our 20 are absent** — MAD JMD DOP
  BSD CRC BZD FJD AWG BBD MVR SCR VND. Four are Emily's new destinations, so
  those entries have tipping data and no convertible rate.
- **Parser brittleness.** `"flying out of Boston"` yields no origin (needs
  `from <city>`); `"a week in Cancun this September"` yields
  `destination_country: "Cancun this September"`. Write the city followed by a
  comma or `for`, and always `from Boston`.
